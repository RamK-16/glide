# Строки переменной высоты (позиции строк и подсказка `changes`): документация правок форка

Этот документ описывает, **что мы доработали в форке glide** для таблиц, у которых `rowHeight`
передан функцией (разная высота строк, автовысота по содержимому). Две правки идут подряд:

- #59 (коммит `7056cf4`, вошёл в 6.9.0): быстрый скролл больших таблиц с rowHeight-функцией.
  Позиции строк считаются один раз и кешируются, видимые строки ищутся по ним двоичным поиском.
- #60 (коммит `4add19a`, вошёл в 6.11.0): подсказка `changes` у `rowHeight`. Когда высоты
  поменялись только у части строк, позиции пересчитываются только от этих строк, а кадр сдвигается
  как при прокрутке и перерисовывается только от первой изменившейся строки вниз.

Здесь: в чём проблема, что было нативным и что добавили мы, публичный API, как проходит пересчёт
позиций и отрисовка, поведение со слитыми блоками, карта кода и тесты.

Планы, отложенное и открытые вопросы (в том числе невоспроизведённый в приложении разрыв слитого
блока) собраны в `plans/row-height-changes.md`.

---

## 1. Проблема и решение

### 1.1 Скролл (#59)

Нативный glide на каждом кадре прокрутки заново складывал высоты всех строк от первой до видимой,
чтобы понять, какие строки сейчас на экране. На строке 900 000 это 900 000 вызовов `rowHeight` за
кадр. Ещё раз все строки обходились при каждом рендере ради общей высоты таблицы. Чем дальше от
начала таблицы, тем медленнее: на миллионе строк кадр доходил до десятков миллисекунд.

```
нативно: каждый кадр                      форк: один раз на новую функцию rowHeight
  y = 0                                     offsets[0] = 0
  for row in 0..rows:                       for row in 0..rows:
      rh = rowHeight(row)                       offsets[row + 1] = offsets[row] + rowHeight(row)
      if scrollY >= y + rh: y += rh; ...
      ...                                   каждый кадр: двоичный поиск по offsets (около 20 шагов)
```

**Решение:** массив верхних границ строк (`getRowOffsets`), двоичный поиск видимых строк по нему
(`getVisibleRows`) и остановка суммирования в `blitLastFrame`, когда сдвиг уже больше экрана.
Публичный API не менялся, таблиц с `rowHeight` числом правка не касается.

### 1.2 Смена высот части строк (#60)

После #59 позиции кешируются по функции `rowHeight`, поэтому при смене высот потребитель обязан
передать новую функцию. На каждую новую функцию glide делал две дорогие вещи: пересчитывал позиции
всех строк и запрещал сдвиг прошлого кадра (`computeCanBlit`), то есть перерисовывал весь экран.
В режиме автовысоты новая функция приходит почти на каждый шаг прокрутки, потому что видимые строки
получают замеренные высоты: на миллионе строк это миллион вызовов `rowHeight` и полный кадр на
каждый шаг.

**Решение:** у функции `rowHeight` появились необязательные поля `version` и `changes`. Если новая
функция говорит «я заменяю версию N, высоты могли поменяться только у строк `from..to`», и glide
видел именно версию N, то позиции обновляются только от этих строк (`updateRowOffsets`), прошлый
кадр сдвигается как обычно, а поверх него перерисовывается область от первой изменившейся строки
вниз (`getChangedRowsRegion`).

## 2. Что нативное в glide, а что добавили МЫ

| Уже было в glide (нативное) | Добавили МЫ (форк) |
|---|---|
| `rowHeight: number \| ((row) => number)` | тип `RowHeightCallback` с полями `version` и `changes`, тип `RowHeightChanges` (экспортируются из пакета) |
| линейный обход строк в `scrolling-data-grid.tsx` на каждый кадр и каждый рендер | `getRowOffsets` + `useRowOffsets` (позиции один раз на функцию, два буфера), `getVisibleRows` (двоичный поиск) |
| `blitLastFrame` складывает высоты всех пролистанных строк | суммирование останавливается, когда сдвиг больше экрана |
| `computeCanBlit`: любая новая функция `rowHeight` запрещает сдвиг кадра | новая функция с подсказкой от прежней версии сдвиг не запрещает (`rowHeightChangesSince`) |
| отрисовка: кадр целиком при смене `rowHeight` | `updateRowOffsets`, `getChangedRowsRegion`, параметр `extraRegions` у `blitLastFrame`, подъём области к началу слитого блока (`spanStartOf`) |

Правила видимости строк не поменялись: частично прокрученная строка, `smoothScrollY`, середина
строки считаются так же, как в старом цикле (это закреплено тестами, которые сравнивают новый поиск
со старым циклом на случайных высотах).

## 3. Публичный API

### 3.1 Контракт: новая функция при смене высот

Позиции строк кешируются по функции `rowHeight`. Когда высоты меняются, нужно передать **новую**
функцию, иначе glide продолжит считать по старым высотам и прокрутка разойдётся с отрисовкой. Это
записано в JSDoc `rowHeight` у `DataEditor`. До #59 glide вызывал функцию заново каждый кадр, и
«старая» функция с новыми ответами работала; теперь нет.

### 3.2 `RowHeightCallback`, `version`, `changes`

```ts
import type { RowHeightCallback, RowHeightChanges } from "@glideappsfinal/glide-data-grid";

const next: RowHeightCallback = Object.assign((row: number) => heights[row], {
    version: 8,
    changes: { previousVersion: 7, from: 120, to: 134 },
});
```

- `version`: номер функции. Должен быть свой у каждой функции одного грида: по совпавшему номеру
  glide считает, что видел именно эту функцию.
- `changes.previousVersion`: номер функции, которую заменяет новая.
- `changes.from`, `changes.to`: первая и последняя строка (границы включительно), у которых высота
  могла измениться. У строк вне диапазона новая функция обязана возвращать те же числа, что и
  прежняя. Пустой диапазон задаётся `from > to`: высоты не менялись.

Сравнение идёт по номеру версии, а не по ссылке на прежнюю функцию, поэтому цепочка функций не
копится в памяти. Подсказка действует на один шаг: если glide не видел версию `previousVersion`
(например, React выбросил промежуточный рендер), всё пересчитывается целиком. Если число строк
другое, подсказка тоже не используется.

Без `version` и `changes` поведение как раньше: каждая новая функция даёт полный пересчёт позиций
и полный кадр.

С `rowGrouping` и `scaleToRem` функцию `rowHeight` внутри `DataEditor` оборачивают, поля на обёртку
не переносятся, подсказка не используется и ускорения нет (записано в JSDoc).

### 3.3 `rowHeightChangesSince`

Внутренний помощник (`row-offsets.ts`), через который все места в glide решают, можно ли верить
подсказке:

```ts
rowHeightChangesSince(current, previous): RowHeightChanges | undefined
```

Возвращает `current.changes`, только если `current` функция, `previous` функция, у обеих есть
`changes` и `version`, и `current.changes.previousVersion === previous.version`. Во всех остальных
случаях `undefined`, значит полный пересчёт. Им пользуются `useRowOffsets`, `computeCanBlit` и
`drawGrid`.

## 4. Как проходит пересчёт позиций

### 4.1 Массив позиций (`row-offsets.ts`)

`offsets` это `Float64Array` длины `rows + 1`: `offsets[i]` сумма высот строк `0..i-1`,
`offsets[rows]` высота всех строк (её читает `scrolling-data-grid.tsx` для высоты скроллера).

- `getRowOffsets(rows, rowHeight, buffer?)`: полный расчёт. Если передан буфер той же длины, он
  перезаписывается, а не выделяется новый.
- `updateRowOffsets(base, rowHeight, from, to, buffer?)`: расчёт от готовых позиций прежней функции.
  Строки до `from` копируются из `base`, высоты спрашиваются только у строк `from..to`, строки ниже
  сдвигаются на разницу `delta` без вызова `rowHeight`. Если `delta === 0`, хвост просто копируется.
  Буфером может быть и сам `base`, тогда обновление идёт на месте. Диапазон за краями обрезается,
  пустой диапазон даёт копию `base`.
- `getVisibleRows(y, height, rowHeight, offsets, smoothScrollY)`: первая видимая строка находится
  двоичным поиском по `offsets` (первая строка, чей низ ниже `y`). Дальше те же правила, что в
  старом цикле: частично прокрученная строка со `smoothScrollY` остаётся видимой и даёт сдвиг `ty`,
  без него пропускается, когда прокручена её середина; нижняя граница добегает по видимым строкам,
  пока середина строки попадает в окно. `rowHeight` вызывается только для видимых строк.

### 4.2 Два буфера (`use-row-offsets.ts`)

`useRowOffsets(rows, rowHeight)` держит два буфера и помнит, какой из них показан (`committed`
ставится в `useLayoutEffect` после коммита). Новый рендер пишет в тот буфер, что не показан. Это
защита от выброшенного рендера: React может отбросить рендер (прерванный transition, Suspense), и
показанная таблица продолжит читать свой буфер, который никто не перезаписал. Баг был найден на
ревью #59 и закрыт тестом `use-row-offsets.test.tsx` (на одном буфере высота скроллера удваивалась).

Выбор пути на каждый новый `rowHeight`:

```
[1] та же функция и то же число строк            позиции не трогаем, отдаём прежние
[2] rowHeightChangesSince(новая, прежняя) есть   updateRowOffsets от прежних позиций
    и число строк прежнее                        (в свободный буфер; если прежние позиции лежат
                                                 в непоказанном буфере, обновляются на месте)
[3] иначе                                        getRowOffsets целиком в свободный буфер
```

«Прежняя» функция здесь та, для которой позиции считались последними (`last`), а не обязательно
показанная.

## 5. Как проходит отрисовка

### 5.1 Сдвиг кадра (`blitLastFrame`, `computeCanBlit`)

`computeCanBlit` решает, можно ли взять прошлый кадр и сдвинуть его. Нативно любая новая функция
`rowHeight` давала `false`. Теперь:

```ts
(current.rowHeight !== last.rowHeight && rowHeightChangesSince(current.rowHeight, last.rowHeight) === undefined)
```

то есть новая функция с подсказкой от прежней версии сдвиг не запрещает. Всё остальное в
`computeCanBlit` как раньше.

В `blitLastFrame` (#59) сумма высот пролистанных строк считается только пока она не превысила
`height + |translateY - last.translateY|`: дальше и так понятно, что кадр перерисуется целиком. У
функции появился параметр `extraRegions` (#60): список областей, которые нужно перерисовать поверх
сдвинутого кадра вдобавок к полосе прокрутки. Они добавляются в `drawRegions`, только если сдвиг
вообще состоялся (ширина и высота копируемой части больше 150 px); иначе список областей пустой и
`drawGrid` рисует весь экран. Без сдвига и без второго буфера холст больше не копируется сам в себя.

### 5.2 Область перерисовки (`getChangedRowsRegion`)

```
[1] drawGrid: computeCanBlit пропустил новую функцию rowHeight
        |
[2] changes = rowHeightChangesSince(rowHeight, lastArg.rowHeight)
        |
[3] getChangedRowsRegion(changes, прокрутка, итоговые строки, прилипшие строки, spanStartOf)
        |   кадр целиком (undefined), если:
        |     прилипшие строки (pinnedRowsCount > 0) или липкий блок на экране (stickySpanInView)
        |     прокрутка прошла через изменившиеся строки: сдвиг кадра считается по их высотам
        |     изменилась итоговая строка (freezeTrailingRows): они прижаты к низу экрана
        |   иначе область от верха первой изменившейся строки до низа экрана:
        |     topRow = max(changes.from, cellYOffset)
        |     поднимаем topRow к началу слитого блока, пока spanStartOf(topRow) < topRow (раздел 6)
        |     y = верх строки topRow с учётом translateY; область {0, y, width, height - y}
        |
[4] blitLastFrame(..., extraRegions: [changedRowsRegion]) сдвигает кадр и отдаёт drawRegions
        |
[5] обычный проход отрисовки под клипом по drawRegions
```

Строки выше первой изменившейся остались на месте, их не трогаем. Если изменилась строка ниже
экрана, область получается нулевой высоты и перерисовывается только полоса прокрутки (если она была).
Если изменилась строка выше экрана, `topRow` упирается в `cellYOffset` и перерисовывается всё тело.

Если вместе с высотами сменилась и прокрутка, область изменившихся строк складывается с полосой от
сдвига внутри `blitLastFrame`. С #61 туда же складываются области смены выделения
(`docs/selection-partial-redraw.md`).

Если `computeCanBlit` вернул номер колонки (ресайз одной колонки), область не считается и кадр
рисуется целиком.

## 6. Слитые блоки (`spanStartOf`)

Слитый по строкам блок (`spanRows`) рисуется одной ячейкой на всю площадь, его подпись выравнивается
по всему блоку (по умолчанию по центру). Если блок начинается выше первой изменившейся строки и
задевает её, он стал выше, и подпись сместилась. Перерисовка от изменившейся строки оставила бы
старую подпись выше границы и нарисовала новую ниже.

```
блок строки 2..8, выросла строка 7           область от строки 7       область от начала блока
┌───────────┐                                ┌───────────┐              ┌───────────┐
│ 2         │                                │ 2         │              │ 2 ▒▒▒▒▒▒▒ │
│ 3         │                                │ 3 старая  │  осталась    │ 3 ▒▒▒▒▒▒▒ │
│ 4 подпись │  центр блока был здесь         │ 4 подпись │  на месте    │ 4 ▒▒▒▒▒▒▒ │
│ 5         │                                │ 5         │              │ 5 подпись │  новый центр
│ 6         │                                │ 6 ▒▒▒▒▒▒▒ │              │ 6 ▒▒▒▒▒▒▒ │
│ 7 (выше)  │                                │ 7 ▒▒▒▒▒▒▒ │  новая       │ 7 ▒▒▒▒▒▒▒ │
│ 8         │                                │ 8 подпись │  подпись     │ 8 ▒▒▒▒▒▒▒ │
└───────────┘                                └───────────┘              └───────────┘
```

Поэтому верх области поднимается к началу такого блока. `drawGrid` передаёт в
`getChangedRowsRegion` функцию `spanStartOf(row)`: она проходит по видимым колонкам
(`effectiveCols`), спрашивает у `getCellContent` ячейку `[col, row]` и возвращает самое верхнее
`spanRows[0]` среди блоков, которые начинаются выше `row` и задевают её; без блока возвращает саму
`row`. `getChangedRowsRegion` повторяет вызов, пока граница не станет чистой (`spanStartOf(topRow)
>= topRow`), поэтому цепочка блоков, стоящих друг на друге, поднимает область до начала самого
верхнего. Если блок начинается выше экрана, `topRow` упирается в `cellYOffset`, перерисовывается
всё тело. Блок учитывается и тогда, когда изменившаяся строка ниже экрана, а сам блок виден:
`topRow` начинается с `changes.from`, и первый же `spanStartOf` поднимает его к началу блока.

Опрос идёт только по строке границы и только по видимым колонкам, ячейки выше или ниже не
спрашиваются.

Блок с `spanAlign.sticky` (подпись прилипает к видимой части) этим путём не идёт: при
`stickySpanInView` кадр рисуется целиком, как и при прокрутке.

Исправление с `spanStartOf` вошло в #60 отдельным коммитом (`3e7213b`) по замечанию ревью. В
приложении-потребителе разрыв блока глазами подтвердить не удалось, разбор в
`plans/row-height-changes.md`.

## 7. Когда всё как раньше (полный пересчёт и полный кадр)

- У новой функции нет `changes`, или у прежней нет `version`, или `previousVersion` не совпал
  (React выбросил рендер, потребитель пропустил шаг).
- Сменилось число строк.
- Прилипшие строки (`stickyRows`) на экране или липкий блок (`spanAlign.sticky`) в кадре.
- Прокрутка за этот же кадр прошла через изменившиеся строки.
- Изменилась высота итоговой строки (`freezeTrailingRows`).
- Ресайз колонки в этом же кадре.
- Вместе с `rowHeight` сменилось что-то ещё из `computeCanBlit` (данные, тема, колонки, выделение
  без #61 и так далее).
- Режим отрисовки `direct` (сдвига кадра там нет вообще).

## 8. Правила, которые нельзя нарушать

**(а) Новая функция на каждую смену высот.** Позиции и кадр кешируются по ссылке на функцию. Смена
высот без новой функции рассинхронизирует прокрутку и отрисовку (на ревью #59 это воспроизвели на
ленивом пересчёте высоты в потребителе: в позициях остался лишний кусок высоты).

**(б) Вне `from..to` высоты те же.** `updateRowOffsets` не спрашивает строки вне диапазона, а
`getChangedRowsRegion` не перерисовывает строки выше `from`. Если потребитель соврал, строки
разойдутся с кадром, и glide этого не заметит.

**(в) `version` уникален в пределах грида.** Совпавший номер для glide значит «та же функция, что я
видел». Повтор номера подставит чужую подсказку.

**(г) Подсказка на один шаг.** `previousVersion` сравнивается с версией функции, для которой
позиции считались последними (`useRowOffsets`) и для которой рисовался прошлый кадр (`drawGrid`,
`lastArg`). Это могут быть разные функции, если рендер выбросили: тогда одна из частей сделает
полный пересчёт, и это нормально.

## 9. Карта кода (что где)

- **`internal/scrolling-data-grid/row-offsets.ts`**: `getRowOffsets` (#59), `getVisibleRows` (#59),
  типы `RowHeightChanges` и `RowHeightCallback` (#60), `rowHeightChangesSince` (#60),
  `updateRowOffsets` (#60).
- **`internal/scrolling-data-grid/use-row-offsets.ts`**: `useRowOffsets`, два буфера, выбор между
  полным и частичным пересчётом.
- **`internal/scrolling-data-grid/scrolling-data-grid.tsx`**: высота скроллера из `offsets[rows]`,
  видимые строки через `getVisibleRows` вместо старого цикла.
- **`internal/data-grid/render/data-grid-render.blit.ts`**: `computeCanBlit` пропускает новую функцию
  с верной подсказкой; `blitLastFrame` обрезает сумму высот и принимает `extraRegions`;
  `getChangedRowsRegion` и `ChangedRowsRegionArgs`.
- **`internal/data-grid/render/data-grid-render.ts`**: в `drawGrid` вызов `getChangedRowsRegion`,
  `spanStartOf` через `getCellContent` по видимым колонкам, передача области в `blitLastFrame`.
