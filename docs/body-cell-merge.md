# Объединение ячеек тела — документация правок форка

Этот документ описывает, **что мы доработали в форке glide** для объединения (слияния)
обычных ячеек таблицы: rowspan и прямоугольные блоки `колонки × строки` с 2D-выравниванием.
Это **не** нативное поведение glide — нативно был только colspan (`cell.span`), фича
добавлена поверх и переиспользует примитивы слитой шапки. Здесь — проблема, что нативное
vs что добавили мы, публичный API, пайплайн, поведение (клики / выделение / навигация /
массовые операции / перерисовка) и карта кода по модулям.

Планы, отложенное и известные баги — в `plans/body-cell-merge.md`.
Слитые ячейки ШАПКИ (spanGroupHeader / spanShallowGroups) — в `docs/header-cell-merge.md`.

---

## 1. Проблема и решение

Нативный glide умеет сливать ячейки только **по горизонтали** (`cell.span` — colspan).
Вертикального слияния (rowspan) и прямоугольных блоков нет, поэтому «excel-подобные»
структуры (шапка-строка на несколько строк данных, сгруппированные значения) собрать нельзя:

```
нативно (только colspan)            нужно (rowspan и прямоугольник)
┌───────────────┬───────┐           ┌───────┬───────┬───────┐
│    colspan    │   C   │           │       │  B1   │       │
├───────┬───────┼───────┤           │   A   ├───────┤ блок  │
│  A1   │  B1   │  C1   │           │(3 стр)│  B2   │ 2×2   │
├───────┼───────┼───────┤           │       ├───────┼───────┤
│  A2   │  B2   │  C2   │           │       │  B3   │  C3   │
└───────┴───────┴───────┘           └───────┴───────┴───────┘
```

**Решение** — поле `spanRows` на ячейке (зеркало `span` для строк). Вместе они задают
прямоугольный блок: рисуется одной ячейкой на всю площадь, контент выравнивается по двум
осям (`spanAlign`), а клики, выделение, навигация и массовые операции понимают блок как
одну логическую ячейку с origin в левом верхнем углу. Всё **opt-in**: без `spanRows`
рендер байт-в-байт как в апстриме (включая нативный colspan).

---

## 2. Что нативное в glide, а что добавили МЫ

Нативный colspan-механизм не ломали — расширили его на вторую ось. Сверено по `origin/main`.

| Уже было в glide (нативное) | Добавили МЫ (форк) |
|---|---|
| `cell.span` (colspan) + дедуп отрисовки по спан-ключу | `cell.spanRows` (rowspan) + прямоугольные блоки `span × spanRows` |
| `getSpanBounds` (геометрия colspan c frozen-сплитом) | `getRowSpanBounds`, `resolveHorizontalSpanArea` (вертикаль + обёртка горизонтали) |
| `expandSelection` расширяет выделение по colspan | расширение по rowspan + `expandRectToSpans` (общая геометрия для выделения и fill-превью) |
| вырез линий сетки под спанами (evenodd-клип) | полосы частичного тинта/фона внутри блока (`SpanBlockGeometry`, `spanPartialFillRect`, `pushSpanSelectionStrips`, `computeSpanRowBgFills`) |
| copy: пустые значения для не-origin колонок спана | то же для покрытых строк rowspan; skip покрытых в fill/paste/delete (`isCoveredSpanCell`) |
| — | `spanAlign` на ячейке (2D-выравнивание, общий примитив со слитой шапкой), `getSpanOrigin`, merged-aware навигация и damage (`getDamageDrawRegions`, `damageHasSpanCells`, `getBodyDamagePad`) |

**Контракт данных:** каждая покрытая ячейка блока обязана вернуть **одинаковые**
`span`/`spanRows` (модель origin-only: контент читается из origin — левого верхнего угла,
`[span[0], spanRows[0]]`). Рендер сам выбирает, кто рисует блок; первая встреченная ячейка
блока рисует, остальные дедупятся по ключу логического прямоугольника.

## 3. Публичный API

Всё задаётся на уровне ячейки (в `getCellContent`), новых пропов у `DataEditor` нет.

### 3.1 Блок (`span` + `spanRows`)

```tsx
getCellContent={([col, row]) => {
  // Блок: колонки 1-2, строки 0-1. ВСЕ четыре ячейки возвращают одинаковые span/spanRows.
  if (col >= 1 && col <= 2 && row <= 1) {
    return {
      kind: GridCellKind.Text,
      data: 'Блок 2×2',            // контент читается из origin (1, 0)
      displayData: 'Блок 2×2',
      allowOverlay: true,
      span: [1, 2],                // диапазон колонок (нативное поле)
      spanRows: [0, 1],            // диапазон строк (наше поле)
    };
  }
  return ...;
}}
```

Чистый rowspan — только `spanRows`; чистый colspan — только `span` (как в апстриме).

### 3.2 Выравнивание (`spanAlign`)

Тот же тип `SpanAlignment`, что у слитой шапки: `{ horizontal?, vertical? }`,
`horizontal: 'left'|'center'|'right'`, `vertical: 'top'|'center'|'bottom'`.

```tsx
return {
  ...,
  spanRows: [0, 2],
  spanAlign: { horizontal: 'center', vertical: 'center' },
};
```

Дефолты: горизонталь — из `contentAlign` (иначе `left`), вертикаль — `center`.
На одиночную (не слитую) ячейку `spanAlign` не влияет. RTL пока не поддержан.

## 4. Как это работает (пайплайн)

```
[1] getCellContent отдаёт span/spanRows на каждой ячейке блока (контракт §2)
        │
[2] НАШЕ: drawCells — первая встреченная ячейка блока рисует его целиком:
        • дедуп по ключу логического прямоугольника (не текущей ячейки)
        • горизонталь: resolveHorizontalSpanArea (colspan, frozen/scrollable сплит)
        • вертикаль: getRowSpanBounds (origin может быть выше вьюпорта — y в минус,
          канва клипует, scroll-safe)
        │
[3] НАШЕ: фон и тинт блока (SpanBlockGeometry, §7-в):
        • базовый фон — из темы БЕЗ row-override (иначе ховер origin-строки залил бы блок)
        • фон строк (getRowThemeOverride) — пополосно (computeSpanRowBgFills)
        • частичное выделение/highlight-регионы — полосами по пересечению
          (spanPartialFillRect), выделение строк/колонок — pushSpanSelectionStrips
        │
[4] НАШЕ: контент рисуется один раз на весь блок, 2D-выравнивание — drawTextCell →
        drawSpanAlignedText (общий примитив со слитой шапкой)
        │
[5] НАШЕ: интеракции понимают блок как одну ячейку (hit-test → origin, выделение
        растёт до границ блоков, навигация перепрыгивает блок, массовые операции
        пишут только в origin) — §5
```

## 5. Поведение

### Клик / hit-test
Клик (и hover) в **любую точку блока** нормализуется к origin: `getMouseArgsForPosition`
читает ячейку и возвращает `location = getSpanOrigin(cell)` с bounds всего блока. Дальше
весь пайплайн (выделение, редактирование, оверлей) работает с origin.

### Выделение
- Одиночный клик выделяет блок целиком: `expandSelection` доводит диапазон до границ
  пересечённых блоков **до неподвижной точки** (`expandRectToSpans`; цепочки блоков
  тянут друг друга). `spanRangeBehavior="allowPartial"` отключает расширение (как нативно).
- `cellIsSelected` / `cellIsInRect` понимают rowspan: выбранная строка внутри `spanRows` =
  выделен весь блок; перекрытие диапазона выделения с блоком считается по обеим осям.
- Focus-обводка рисуется вокруг **всего блока** (identity выделения — origin, растяжение
  диапазона рамки чисто визуальное, в `data-editor.tsx`).
- Частичное выделение (диапазон накрывает блок не целиком, выделение строк/колонок) НЕ
  заливает весь блок — красится полосами по пересечению (§4 шаг 3).
- Смена данных: если правка пересобрала блоки и блок под фокусом вырос, диапазон
  выделения дорастает до его границ сам (эффект в `data-editor.tsx`; только расширение,
  `allowPartial` уважается). Ctrl-стек диапазонов не дорастает — принятое ограничение (§9).

### Клавиатурная навигация
Один шаг стрелкой **перепрыгивает блок**: по оси движения берётся дальняя грань блока
origin-ячейки, приземление нормализуется к origin блока-соседа (как клик). Покрытые
ячейки недостижимы с клавиатуры.

Поперёк движения работает **память полосы** (как в Excel): горизонтальный ход сквозь
высокий блок помнит строку входа и выходит на неё, а не на верхнюю строку блока;
вертикальный ход сквозь широкий блок так же помнит колонку входа. Ход по своей оси
задаёт полосу заново (строка запоминается после пропуска строк-заголовков групп);
клик мышью и прыжки в начало/конец память сбрасывают (`arrowLaneRef`).

### Редактор и превью
Оверлей редактора и превью открываются по вертикальному выравниванию блока
(`spanAlign.vertical`): верх, центр или низ; высота оверлея остаётся в одну строку.
Если низ блока прокручен за экран и его границы недоступны, открываемся по верхней
строке (тихий откат). Точка встройки одна на все оверлеи — `setOverlaySimple`.

### Массовые операции (fill / copy / paste / delete)
Инвариант origin-only-write (§7-а): запись только в origin, покрытые координаты
пропускаются через `isCoveredSpanCell`. Copy отдаёт значение в origin-позиции, для
покрытых — пустые ячейки буфера (зеркало нативного colspan-поведения). Fill-handle:
квадратик рисуется под всем блоком (низ = `spanRows[1]`), пунктир протяжки прилипает
к границам блоков (`expandRectToSpans`), запись протяжки скипает покрытые.

### Frozen-колонки
Блок, пересекающий границу freeze, рисуется в двух областях (frozen + scrollable,
`getSpanBounds`); контент не дублируется (`skipContents`). Полосы тинта клэмпятся в
видимую часть блока.

## 7. Инварианты (дорого дались — НЕ сломать)

**(а) Origin-only-write.** Любая запись (fill, paste, delete, протяжка) идёт ТОЛЬКО в
origin блока; покрытые координаты пропускаются (`isCoveredSpanCell`) во ВСЕХ трёх местах
`data-editor.tsx`. Пропустишь одно — значение улетает «в середину блока» и данные
потребителя расходятся с отображением.

**(б) Damage на весь блок + раздельные repair-pad'ы.** Блок рисуется целиком, поэтому и
damage-регион обязан покрывать весь блок (`getDamageDrawRegions`), иначе оверлеи
(рамка/подсветка/fill-handle) восстановятся по одной ячейке и «пропадут» на остальной
площади. Ручной damage-путь включается при ЛЮБОЙ span-ячейке в damage
(`damageHasSpanCells`), НЕ только при `enableLowDprHairline`. При этом pad тела
(`getBodyDamagePad` ≥ 1 при спанах) отделён от pad'а шапки (`getDamageRepairPad` = 0 без
low-DPR): общий ненулевой pad раздувает `clipHeaderDamage` и рисует светлую полосу на
выделенной группе (см. header-док §7-8).

**(в) Полосы — от полного диапазона блока.** Все полосы (тинт выделения, фон строк)
считаются от логического диапазона блока, а НЕ от строки/колонки, инициировавшей
отрисовку. Иначе при damage-перерисовке от невыделенной покрытой ячейки полосы
«осыпаются» (ховер соседних ячеек стирал выделение блока). Геометрия собрана в
`SpanBlockGeometry` — один объект на блок, все хелперы считают от него.

## 8. Тонкие места, пойманные в ходе разработки

Хронология фиксов ветки `feat/span-cells` (после базовой реализации):

- **Клик по покрытой ячейке мимо блока.** Нормализация к origin сначала стояла слишком
  широко (ломала OOB/header-ветки), затем — точечно в cell-ветке `getMouseArgsForPosition`.
- **Ховер стирал рамку выделения и fill-handle.** Damage-перерисовка блока затирала
  оверлеи своей заливкой. Первое поколение фикса дорисовывало рамки и ручку прямыми
  вызовами в общей damage-ветке; после появления маршрута `damageHasSpanCells` (кадры
  со слитыми ячейками идут клип-путём со своей дорисовкой) эти вызовы стали лишней
  работой на обычных таблицах и удалены — общая ветка вернулась к поведению апстрима.
- **Fill-handle и превью протяжки.** Квадратик — под низом блока (`spanRows[1]`);
  пунктир протяжки прилипает к границам блоков тем же `expandRectToSpans`, что и запись
  (иначе превью и результат расходились).
- **Рамка на настоящем крае ячейки.** Апстримный «−1 от края» применяется только когда
  край упирается в канву — иначе рамка отъезжала от бордера на последней колонке/строке.
- **Частичный тинт.** Выделение/highlight-регион, накрывающий блок частично, красил весь
  блок → полосы по пересечению (`intersectRangeWithSpan` + `spanPartialFillRect`), затем
  то же для нативных range-акцентов и выделения строк/колонок (`pushSpanSelectionStrips`,
  полосы от полного диапазона блока — §7-в), затем пополосный фон строк
  (`computeSpanRowBgFills`) и accent контента origin (`isSpanOriginAccented`).
- **Границы блока пропадали на ховере без `enableLowDprHairline`.** Ручной span-repair
  damage-путь был загейчен этим флагом; введены `damageHasSpanCells` +
  `getBodyDamagePad` (§7-б) — путь включается при спанах в damage независимо от флага.
- **Многострочное копирование colspan (унаследованный баг апстрима).** Номер колонки
  origin сравнивался со списком колонок по номеру строки; со второй строки покрытые
  колонки не затирались (дубли и потери значений при вставке). Сравнение переведено
  на колонку самой ячейки.
- **Полоса выделения на блоке через границу закрепления.** Пиксель `x` прокручиваемой
  части блока соответствует первой незакреплённой колонке, а цикл полосы шёл от первой
  колонки блока — ширины закреплённых колонок прибавлялись дважды и полоса съезжала
  вправо. В `SpanBlockGeometry` добавлен `xStartCol`.
- **Создание объектов в горячем цикле отрисовки.** Диапазоны и геометрия блока
  создаются один раз на отрисовываемый блок, а не на каждую посещённую ячейку
  (апстрим прямо предупреждает про цену выделения памяти в этом цикле).

## 9. Ограничения и «что дальше»

- Ctrl-стек диапазонов не дорастает до выросшего блока — дорастает только текущий
  диапазон (стек ведёт себя как у кликов; принятое ограничение).
- RTL-выравнивание, латентный `getSpanBounds` под DnD-реордером (унаследован от
  нативного colspan), слияние в subRows-дереве — см. `plans/body-cell-merge.md`.
