# Объединение ячеек тела — документация правок форка

Этот документ описывает, **что мы доработали в форке glide** для объединения (слияния)
обычных ячеек таблицы: rowspan и прямоугольные блоки `колонки × строки` с выравниванием по двум осям.
Это **не** нативное поведение glide — нативно был только colspan (`cell.span`), фича
добавлена поверх и переиспользует наработки слитой шапки. Здесь: в чём проблема, что было
нативным и что добавили мы, публичный API, как проходит отрисовка, поведение (клики,
выделение, навигация, массовые операции, перерисовка) и карта кода по модулям.

Планы, отложенное и известные баги — в `plans/body-cell-merge.md`.
Слитые ячейки ШАПКИ (spanGroupHeader / spanShallowGroups) — в `docs/header-cell-merge.md`.

---

## 1. Проблема и решение

Нативный glide умеет сливать ячейки только **по горизонтали** (`cell.span` — colspan).
Вертикального слияния (rowspan) и прямоугольных блоков нет, поэтому «excel-подобные»
структуры (шапка-строка на несколько строк данных, сгруппированные значения) собрать нельзя:

```
нативно (только colspan)            нужно (rowspan и прямоугольник)
┌───────────────┬───────┐           ┌───────┬───────┬───────┐
│    colspan    │   C   │           │       │  B1   │       │
├───────┬───────┼───────┤           │   A   ├───────┤ блок  │
│  A1   │  B1   │  C1   │           │(3 стр)│  B2   │ 2×2   │
├───────┼───────┼───────┤           │       ├───────┼───────┤
│  A2   │  B2   │  C2   │           │       │  B3   │  C3   │
└───────┴───────┴───────┘           └───────┴───────┴───────┘
```

**Решение** — поле `spanRows` на ячейке (то же, что `span`, только для строк). Вместе они
задают прямоугольный блок: он рисуется одной ячейкой на всю площадь, контент выравнивается по
двум осям (`spanAlign`), а клики, выделение, навигация и массовые операции понимают блок как
одну логическую ячейку. Её якорь — верхняя-левая ячейка блока; дальше зовём её первой ячейкой
блока. Всё включается по желанию (opt-in): без `spanRows` отрисовка байт-в-байт как в апстриме
(включая нативный colspan).

## 2. Что нативное в glide, а что добавили МЫ

Нативный colspan-механизм не ломали — расширили его на вторую ось. Сверено по `origin/main`.

| Уже было в glide (нативное) | Добавили МЫ (форк) |
|---|---|
| `cell.span` (colspan) + защита от повторной отрисовки по спан-ключу | `cell.spanRows` (rowspan) + прямоугольные блоки `span × spanRows` |
| `getSpanBounds` (геометрия colspan с делением по границе закрепления) | `getRowSpanBounds`, `resolveHorizontalSpanArea` (вертикаль + обёртка горизонтали) |
| `expandSelection` расширяет выделение по colspan | расширение по rowspan + `expandRectToSpans` (общая геометрия для выделения и превью протяжки) |
| вырез линий сетки под спанами (evenodd-клип) | полосы частичной заливки выделения и фона внутри блока (`SpanBlockGeometry`, `spanPartialFillRect`, `pushSpanSelectionStrips`, `computeSpanRowBgFills`) |
| copy: пустые значения для не-первых колонок спана | то же для покрытых строк rowspan; пропуск покрытых в fill/paste/delete (`isCoveredSpanCell`) |
| — | `spanAlign` на ячейке (выравнивание по двум осям, общий помощник со слитой шапкой), `getSpanOrigin`, навигация и damage с пониманием блоков (`getDamageDrawRegions`, `damageHasSpanCells`, `getBodyDamagePad`) |

**Контракт данных:** каждая покрытая ячейка блока обязана вернуть **одинаковые**
`span`/`spanRows` (модель «данные только в первой ячейке»: контент читается из первой ячейки
блока — верхнего-левого угла, `[span[0], spanRows[0]]`). Отрисовка сама выбирает, кто рисует
блок: первая встреченная ячейка блока рисует, остальные пропускаются по ключу логического
прямоугольника (защита от повторного рисования).

## 3. Публичный API

Всё задаётся на уровне ячейки (в `getCellContent`), новых пропов у `DataEditor` нет.

### 3.1 Блок (`span` + `spanRows`)

```tsx
getCellContent={([col, row]) => {
  // Блок: колонки 1-2, строки 0-1. ВСЕ четыре ячейки возвращают одинаковые span/spanRows.
  if (col >= 1 && col <= 2 && row <= 1) {
    return {
      kind: GridCellKind.Text,
      data: 'Блок 2×2',            // контент читается из origin (1, 0)
      displayData: 'Блок 2×2',
      allowOverlay: true,
      span: [1, 2],                // диапазон колонок (нативное поле)
      spanRows: [0, 1],            // диапазон строк (наше поле)
    };
  }
  return ...;
}}
```

Чистый rowspan — только `spanRows`; чистый colspan — только `span` (как в апстриме).

### 3.2 Выравнивание (`spanAlign`)

Тот же тип `SpanAlignment`, что у слитой шапки: `{ horizontal?, vertical? }`,
`horizontal: 'left'|'center'|'right'`, `vertical: 'top'|'center'|'bottom'`. Выравнивание по
двум осям.

```tsx
return {
  ...,
  spanRows: [0, 2],
  spanAlign: { horizontal: 'center', vertical: 'center' },
};
```

По умолчанию: по горизонтали — из `contentAlign` (иначе `left`), по вертикали — `center`.
На одиночную (не слитую) ячейку `spanAlign` не влияет. Письмо справа налево (RTL) пока не
поддержано.

## 4. Как проходит отрисовка

```
[1] getCellContent отдаёт span/spanRows на каждой ячейке блока (контракт §2)
        │
[2] НАШЕ: drawCells — первая встреченная ячейка блока рисует его целиком:
        • защита от повторного рисования по ключу логического прямоугольника (не текущей ячейки)
        • по горизонтали: resolveHorizontalSpanArea (colspan, деление на закреплённую и
          прокручиваемую часть)
        • по вертикали: getRowSpanBounds (первая ячейка блока может быть выше видимой области —
          y уходит в минус, канва обрезает, безопасно при прокрутке)
        │
[3] НАШЕ: фон и заливка блока (SpanBlockGeometry, §7-в):
        • базовый фон — из темы БЕЗ подмены по строке (иначе наведение на первую строку залило
          бы весь блок)
        • фон строк (getRowThemeOverride) — по полосам (computeSpanRowBgFills)
        • частичное выделение и highlight-области — полосами по пересечению (spanPartialFillRect),
          выделение строк/колонок — pushSpanSelectionStrips
        │
[4] НАШЕ: контент рисуется один раз на весь блок, выравнивание по двум осям — drawTextCell →
        drawSpanAlignedText (общий помощник со слитой шапкой)
        │
[5] НАШЕ: интеракции понимают блок как одну ячейку (клик попадает в первую ячейку блока,
        выделение растёт до границ блоков, навигация перепрыгивает блок, массовые операции
        пишут только в первую ячейку) — §5
```

## 5. Поведение

### Клик и попадание клика
Клик (и наведение) в **любую точку блока** переносится в первую ячейку блока:
`getMouseArgsForPosition` читает ячейку и возвращает `location = getSpanOrigin(cell)` с
границами всего блока. Дальше вся цепочка (выделение, редактирование, окно редактора) работает
с первой ячейкой блока.

### Выделение
- Одиночный клик выделяет блок целиком: `expandSelection` доводит диапазон до границ
  пересечённых блоков, повторяя это, пока диапазон не перестанет расти (`expandRectToSpans`;
  цепочки блоков тянут друг друга). `spanRangeBehavior="allowPartial"` отключает расширение
  (как нативно).
- `cellIsSelected` / `cellIsInRect` понимают rowspan: если выбранная строка попадает внутрь
  `spanRows` — выделен весь блок; пересечение диапазона выделения с блоком считается по обеим
  осям.
- Рамка фокуса рисуется вокруг **всего блока** (само выделение стоит в первой ячейке блока,
  а растяжение рамки до границ блока — чисто визуальное, в `data-editor.tsx`).
- Частичное выделение (диапазон накрывает блок не целиком, выделение строк/колонок) НЕ
  заливает весь блок — красится полосами по пересечению (§4 шаг 3).
- Смена данных: если правка пересобрала блоки и блок под фокусом вырос, диапазон
  выделения дорастает до его границ сам (эффект в `data-editor.tsx`; только расширение,
  `allowPartial` соблюдается). Набор диапазонов через Ctrl не дорастает — это принятое
  ограничение (§9).

### Клавиатурная навигация
Один шаг стрелкой **перепрыгивает блок**: по направлению движения берётся дальняя грань блока,
а приземление переносится в первую ячейку соседнего блока (как клик). Покрытые ячейки с
клавиатуры недостижимы.

Есть **память строки и колонки входа** (как в Excel). Идёшь вправо или влево сквозь
высокий блок — таблица помнит, с какой строки ты в него вошёл, и выход ставит курсор
на неё, а не на верхнюю строку блока. Идёшь вверх или вниз сквозь широкий блок — так
же помнится колонка входа. Шаг вверх или вниз запоминает новую строку (уже после
пропуска строк-заголовков групп), шаг вправо или влево — новую колонку. Клик мышью
и прыжки в начало или конец таблицы память сбрасывают (`arrowLaneRef`).

### Редактор и превью
Редактор и превью открываются там, где стоит контент блока по вертикали
(`spanAlign.vertical`): вверху, по центру или внизу; высота окна редактора остаётся
в одну строку. Если низ блока прокручен за экран, открываемся по верхней строке.
Всё это в одном месте — `setOverlaySimple`, через него открывается любой редактор.

### Массовые операции (fill / copy / paste / delete)
Правило «пишем только в первую ячейку блока» (§7-а): запись идёт только в первую ячейку,
покрытые координаты пропускаются через `isCoveredSpanCell`. Copy отдаёт значение из первой
ячейки, а для покрытых кладёт в буфер пустые ячейки (так же ведёт себя нативный colspan).
Ручка протяжки (fill-handle): квадратик рисуется под всем блоком (низ = `spanRows[1]`), пунктир
протяжки прилипает к границам блоков (`expandRectToSpans`), а сама запись протяжки покрытые
ячейки пропускает.

### Закреплённые колонки
Блок, пересекающий границу закрепления, рисуется в двух областях — в закреплённой и
прокручиваемой (`getSpanBounds`); контент при этом не дублируется (`skipContents`). Полосы
заливки выделения обрезаются по видимой части блока.

## 7. Правила, которые нельзя нарушать (дались дорого)

**(а) Пишем только в первую ячейку блока.** Любая запись (fill, paste, delete, протяжка) идёт
ТОЛЬКО в первую ячейку блока; покрытые координаты пропускаются (`isCoveredSpanCell`) во ВСЕХ
трёх местах `data-editor.tsx`. Пропустишь одно — значение улетает «в середину блока», и данные
потребителя расходятся с тем, что видно на экране.

**(б) Частичная перерисовка (damage) на весь блок + раздельные запасы на восстановление.**
Блок рисуется целиком, поэтому и область damage обязана покрывать весь блок
(`getDamageDrawRegions`), иначе рамка, подсветка и ручка протяжки восстановятся по одной ячейке
и «пропадут» на остальной площади. Ручной путь damage включается при ЛЮБОЙ слитой ячейке в
damage (`damageHasSpanCells`), а НЕ только при `enableLowDprHairline`. При этом запас у тела
(`getBodyDamagePad` ≥ 1 при спанах) отделён от запаса у шапки (`getDamageRepairPad` = 0 без
low-DPR): общий ненулевой запас раздувает `clipHeaderDamage` и рисует светлую полосу на
выделенной группе (см. header-док §7-8).

**(в) Полосы считаем от полного диапазона блока.** Все полосы (заливка выделения, фон строк)
считаются от логического диапазона блока, а НЕ от строки или колонки, с которой началась
отрисовка. Иначе при частичной перерисовке от невыделенной покрытой ячейки полосы «осыпаются»
(наведение на соседние ячейки стирало выделение блока). Геометрия собрана в `SpanBlockGeometry`
— один объект на блок, все помощники считают от него.

## 8. Тонкие места, пойманные в ходе разработки

Хронология фиксов ветки `feat/span-cells` (после базовой реализации):

- **Клик по покрытой ячейке мимо блока.** Перенос клика в первую ячейку блока сначала стоял
  слишком широко (ломал ветки «клик вне таблицы» и «клик по шапке»), потом его перенесли
  точечно в ветку ячейки в `getMouseArgsForPosition`.
- **Наведение стирало рамку выделения и ручку протяжки.** Перерисовка блока затирала их своей
  заливкой. Сначала чинили прямой дорисовкой рамок и ручки в общей ветке damage. Позже появился
  отдельный путь для кадров со слитыми ячейками (`damageHasSpanCells`), который дорисовывает всё
  сам, поэтому старые вызовы стали лишней работой для обычных таблиц и были удалены — общая
  ветка вернулась к поведению апстрима.
- **Ручка протяжки и превью протяжки.** Квадратик — под низом блока (`spanRows[1]`); пунктир
  протяжки прилипает к границам блоков тем же `expandRectToSpans`, что и запись (иначе превью и
  результат расходились).
- **Рамка на настоящем крае ячейки.** Апстримный сдвиг «−1 от края» применяется только когда
  край упирается в канву, иначе рамка отъезжала от бордера на последней колонке или строке.
- **Частичная заливка выделения.** Выделение или highlight-область, накрывающая блок частично,
  красила весь блок — исправили на полосы по пересечению (`intersectRangeWithSpan` +
  `spanPartialFillRect`), затем то же для нативных акцентов диапазона и выделения строк/колонок
  (`pushSpanSelectionStrips`, полосы от полного диапазона блока — §7-в), затем фон строк по
  полосам (`computeSpanRowBgFills`) и акцент контента первой ячейки (`isSpanOriginAccented`).
- **Границы блока пропадали при наведении без `enableLowDprHairline`.** Ручной путь damage для
  восстановления границ блока был завязан на этот флаг; ввели `damageHasSpanCells` +
  `getBodyDamagePad` (§7-б) — путь включается при спанах в damage независимо от флага.
- **Копирование нескольких строк с colspan (унаследованный баг апстрима).** Номер колонки
  первой ячейки сравнивался со списком колонок по номеру строки; со второй строки покрытые
  колонки не затирались (при вставке появлялись дубли и терялись значения). Сравнение перевели
  на колонку самой ячейки.
- **Полоса выделения на блоке через границу закрепления.** Пиксель `x` прокручиваемой части
  блока соответствует первой незакреплённой колонке, а цикл полосы шёл от первой колонки блока
  — ширины закреплённых колонок прибавлялись дважды, и полоса съезжала вправо. В
  `SpanBlockGeometry` добавили `xStartCol`.
- **Создание объектов в горячем цикле отрисовки.** Диапазоны и геометрия блока создаются один
  раз на отрисовываемый блок, а не на каждую посещённую ячейку (апстрим прямо предупреждает про
  цену выделения памяти в этом цикле).

## 9. Ограничения и «что дальше»

- Набор диапазонов через Ctrl не дорастает до выросшего блока — дорастает только текущий
  диапазон (набор ведёт себя так же, как клики; принятое ограничение).
- Выравнивание для письма справа налево, скрытая болячка `getSpanBounds` при перетаскивании
  колонок (унаследована от нативного colspan), слияние в дереве subRows — см.
  `plans/body-cell-merge.md`.
